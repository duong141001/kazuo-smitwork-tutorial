Phần 1 — Template Test Case

1.1. Cấu trúc 1 test case

1.2. Quy tắc viết test case

  • 1 case = 1 mục tiêu kiểm. Không gộp nhiều mục tiêu.
  • Bước phải tái lập được: người khác đọc làm lại y hệt.
  • Kết quả kỳ vọng đo được: ghi cụ thể cái nhìn thấy, tránh "chạy ổn".
  • Không đoán khi thiếu spec: thiếu luật/số → ghi "Q&A gửi GD/Dev".

1.3. Quy ước mã module

TC-BAG-*Túi đồ / trang bị

Phần 2 — Các luồng test

2.1. Bốn loại test & khi nào dùng

LoạiKiểm cái gìVí dụ
Functional1 chức năng đúng đặc tảBấm X → ra Y
IntegrationNhiều tính năng ghép nối đúngXong A mở khóa B
Edge CasesBiên, input bất thườngTúi đầy, mất mạng giữa chừng
PerformanceTốc độ, tải, độ mượtNhiều đối tượng cùng lúc

2.2. Ba luồng test chuẩn

A · Smoke

  • Chạy ngay khi nhận build
  • Fail → trả build, dừng test

B · Functional đầy đủ

  • Toàn bộ case Functional + Edge Cases
  • Chạy sau khi smoke pass

C · Regression

  • Checklist cố định mỗi module
  • + case liên quan bug vừa fix
  • Chạy sau mỗi bản vá / build mới

Phần 3 — Quy trình test của phòng QA

3.1. Vòng đời 1 lần kiểm thử (6 bước)

BướcViệcĐầu ra
1Đọc đặc tả — bóc input/luật/outputĐiểm cần kiểm + Q&A GD
2Viết test case theo templateBộ test case
3Chuẩn bị build + tài khoản + thiết bịMôi trường sẵn sàng
4Thực thi, chụp ảnh/clipKết quả thực tế
5Ghi Pass/Fail/Blocked; Fail → log bugBáo cáo + bug log
6Regression sau bản váXác nhận không hồi quy

3.2. Mức độ lỗi (Severity)

MứcĐịnh nghĩaXử lý
BlockerChặn luồng chính, không chơi tiếpFix trước release
CriticalSai logic nghiêm trọngFix trong phase
MajorẢnh hưởng trải nghiệm rõCân nhắc theo timeline
MinorLỗi nhỏ, cosmeticBacklog

3.3. Bug report chuẩn

  • Tiêu đề: ngắn, hiện tượng · Môi trường: build số, thiết bị
  • Bước tái hiện (đánh số) · Thực tế vs Kỳ vọng
  • Severity + ảnh/clip · Tần suất: luôn / thỉnh thoảng

3.4. Tiêu chí Vào / Ra

Entry: có build pass smoke · tính năng dev xong · đã có test case.

Exit: 100% case High Pass · không còn Blocker/Critical · bug còn lại đã log & được chấp nhận hoãn.

3.5. Vòng đời trạng thái test case

Chưa chạy → Đang chạy → Pass
                      → Fail → (Dev fix) → Re-test → Pass
                      → Blocked (thiếu điều kiện / chặn bởi bug khác)
Việc còn treo & Q&A
  • Chờ GDD/Feature Spec để điền test case cụ thể.
  • Cần PM / QA Lead duyệt template + quy trình trước khi áp dụng toàn phòng.

Q&A cần làm rõ:

  1. Công cụ quản lý test case + bug dùng gì (KazuoTask, Excel, TestRail...)?
  2. Định mức EST/loại test của phòng có chuẩn riêng chưa?
  3. Checklist regression cố định mỗi module do ai chốt?
